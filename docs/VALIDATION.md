## Подготовка контейнера

Собран Linux/amd64-образ `obhush:2026-10-26` на Node.js 24.19.0 Alpine с закреплённым digest базового образа. При сборке повторно выполнены TypeScript/build и все 16 проверок. Сборка выполнялась в облачной среде разработки, не на клиентском VPS. Штатный прокси и его доверенный CA передавались временными BuildKit secrets; проверка TLS и npm integrity сохранялась.

Контейнер запущен в отдельном тестовом Compose-проекте. Все 6 браузерных сценариев повторены против контейнера — успешно. Реальные ограничения проверены через Docker API: 512 MiB RAM, столько же MemorySwap (без дополнительного swap), 0,5 CPU, CPU shares 128, OOM score +500, PIDs 96, read-only root, UID 1000, публикация только 127.0.0.1. Проверены защищённая корневая ФС, запись в отдельный том и отсутствие встроенного `.env`/ключа. Один замер RSS после проверок: около 51 MiB; это не измерение максимума под произвольной нагрузкой.

Прямое SSH-подключение к клиентскому VPS из этой среды недоступно. Пользователь выполнил проверенный приватный установщик в своём терминале и получил `PRIVATE_READY`: приложение здорово, существующий прокси может до него достучаться, идентификаторы/время запуска/restart count защищённых контейнеров не изменились. На приватном этапе общий Caddyfile не редактировался. Это не является гарантией отсутствия риска при любой будущей нагрузке.

Приватный установщик проверен отдельно на изолированном Docker-стенде: существующий сайт продолжал отвечать, файл прокси оставался байт-в-байт прежним, новый контейнер запускался с лимитами ресурсов. Скачиваемые образ и Compose закреплены SHA256; сборка и установка пакетов на VPS не выполняются.

Публикация домена проверена на отдельном стенде с Caddy 2.10.2: существующий HTTPS-сайт и новый HTTPS-сайт работают после плавной загрузки конфигурации, защищённые контейнеры не перезапускаются, inode привязанного Caddyfile сохраняется. В тесте использовался доверенный тестовый CA Caddy, без отключения TLS-проверки. Отдельно внедрён сбой нового сайта: исходный файл восстановлен байт-в-байт, существующий HTTPS-сайт продолжает отвечать, контейнеры не перезапущены. Публичный сертификат реального домена проверяется отдельно при запуске на VPS.
