# Размещение рядом с действующим клиентским приложением

Публичный сайт: **https://obihush.site**. Размещение выполнено отдельным Compose-проектом с лимитами ресурсов. Существующие HTTPS-сайты проверены до и после подключения домена; защищённые контейнеры не перезапускались. Результаты — в `docs/VALIDATION.md`.

Доступность основного сервиса и его бота — обязательное условие. У ОБҲУШ собственные база файлов, том и Docker-сеть. Общими остаются хост, диск и ядро: ограничения ресурсов уменьшают влияние, но не дают гарантии при любой нагрузке.

## Сначала только проверка

Скрипт `deploy/audit-vps.sh` только читает состояние. Он не устанавливает Docker, не вызывает PM2, не печатает окружение/аргументы процессов/логи/токены, не меняет Nginx, firewall или службы.

С компьютера, где уже настроен SSH:

```bash
ssh -p SSH_PORT SSH_USER@VPS_IP 'bash -s' < deploy/audit-vps.sh
```

Отсутствующий или недоступный компонент — неизвестность, а не доказательство его отсутствия. В отчёте PM2 указаны сохранённые метаданные; они сами по себе не доказывают текущее здоровье процесса. После отчёта отдельно устанавливаются способ запуска сайта/бота, их контрольные показатели, резервные копии, обычная и пиковая нагрузка. Нельзя считать один замер доказательством запаса на пике.

Размещение на этом VPS откладывается, если ресурсов мало, неизвестна нагрузка, нет надёжного способа проверить основной сервис, нужна установка/перенастройка системных компонентов или нельзя гарантированно остановить только ОБҲУШ. Установка Docker на рабочий VPS может менять сеть; не делать её автоматически.

## Подготовленный изолированный запуск

`deploy/compose.yml` задаёт отдельный проект `obhush`:

- Только заранее собранный образ; сборки на клиентском сервере нет.
- По умолчанию порт `127.0.0.1:43100`. Установщик для существующего контейнерного Caddy использует проверенный адрес шлюза его Docker-сети на порту 43100: прокси может подключиться, а приложение сохраняет отдельную сеть. Новые слушатели на внешних 80/443 не создаются.
- CPU не более 0,5 ядра, RAM не более 512 MiB, swap для контейнера не добавляется, максимум 96 процессов.
- Относительный CPU-вес 128 (ниже обычного 1024) и положительный OOM score: ОБҲУШ получает более низкий приоритет при конкуренции за ресурсы. Это не заменяет проверку поведения хоста под нагрузкой.
- Непривилегированный пользователь, read-only корневая ФС, удалённые capabilities, no-new-privileges.
- Собственный том `obhush_runtime`, без доступа к данным основного сервиса, Docker-сокету или каталогам хоста.
- Логи ограничены 10 MB, не более трёх автоматических перезапусков при ошибке.

Параметры — первоначальный бюджет, а не вывод о пригодности конкретного VPS. Они проверяются под нагрузкой вне клиентского сервера. Архитектура образа должна совпадать с VPS.

Образ собирается в отдельной среде разработки:

```bash
docker build -t obhush:2026-10-26 .
docker save -o obhush.image.tar obhush:2026-10-26
```

`.dockerignore` исключает `.env`, runtime.env, Git, результаты тестов и архивы. Секрет не попадает в образ. Конфигурация Compose намеренно запрещает автоматический pull и не содержит build.

После положительного аудита и подготовки отдельного каталога можно перенести образ, `deploy/compose.yml` и приватный `runtime.env`. Ключ переносится безопасно файлом с правами 0600, без вывода в терминал и без записи в Git. До запуска проверяются свободный порт, свободный диск для распаковки образа, ресурсный запас и уже работающий Docker. Загрузка образа тоже создаёт дисковую нагрузку — её нельзя считать бесплатной для клиентского хоста.

Проверка Compose без вывода значений переменных: `docker compose -f deploy/compose.yml config --quiet`. Не публикуйте полный `docker compose config`: он может раскрыть env_file.

До и после запуска фиксируется состояние основного сервиса; его процессы, конфигурация и данные не меняются. Пробный период должен включать собственные функциональные запросы ОБҲУШ и наблюдение за ресурсами/ошибками сайта и бота. Тестовые сообщения клиентам или заказы не создаются.

Для первой закрытой проверки не нужен домен и не требуется менять Nginx:

```bash
ssh -p SSH_PORT -L 8080:127.0.0.1:43100 SSH_USER@VPS_IP
```

После этого приложение доступно через локально перенаправленный порт 8080 на компьютере проверяющего. Это личный SSH-туннель, а не публичный адрес сайта.

## Публичный адрес — отдельный этап

Новый домен только даёт адрес; он не изолирует ресурсы. `deploy/publish_domain.py` проверяет DNS, приватное приложение, исходный Caddyfile и существующие HTTPS-сайты. После валидации кандидатной конфигурации скрипт сохраняет резервную копию в каталоге ОБҲУШ и дописывает один блок сайта, сохраняя inode привязанного файла. Выполняется `caddy reload`, без перезапуска контейнера. При ошибке восстанавливается исходный файл, если он не был параллельно изменён другим оператором.

Входные параметры — домен, IP сервера и точный путь привязанного Caddyfile. Они передаются оператором, не вшиты в установщик. По умолчанию скрипт выполняет только проверки; применение требует флага `--apply`. Повторно добавлять уже опубликованный домен не нужно: скрипт остановится, чтобы избежать дубликата.

Помощник ограничивает частоту запросов и использует только бесплатные модели. Лимиты провайдера могут исчерпаться: тогда интерфейс явно сообщает о локальном расчётном ответе. Существующие домены, сертификаты, сайт, база и бот основного сервиса не перенастраиваются. Не запускать certbot --nginx и не обновлять системные пакеты для этого приложения.

## Остановка только ОБҲУШ

Для установки в стандартный каталог остановка только ОБҲУШ:

```bash
docker compose -p obhush -f /opt/obhush/compose.yml stop
```

Команда оставляет данные и существующие проекты на месте; домен ОБҲУШ будет временно возвращать ошибку upstream. При ухудшении показателей прекращаются тесты и проверяются основной сервис и причина ухудшения. Не использовать `docker system prune`, глобальные PM2-команды, остановку Docker daemon или перезапуск всего VPS.

До работы на сервере нужно подтвердить конкретные каталог, порт, образ, контрольные показатели и процедуру удаления только ресурсов проекта `obhush`.
